# Flow Field 전환 — 통합 체크리스트

## Context

벽(Wall) 물리 콜라이더(radius=0.4)와 그리드 점유 영역(2x2=2.0x2.0) 사이 불일치로 인해 Tank/EnemyBig 등 대형 유닛이 벽 사이 갭을 물리적으로 통과하는 버그가 발생. 근본 원인은 NavMesh/Grid/Physics 3중 데이터 소스의 불일치이며, NavMeshObstacle(managed GameObject)이 DOTS 패러다임에도 맞지 않음. 그리드를 경로 탐색의 단일 진실 소스로 만들고, Flow Field로 전환하여 다수 유닛 이동 성능도 확보한다.

**기획 원칙**: 유닛 간 밀기(displacement) 불가 — hardPush는 이미 제거됨 (soft separation만 사용).

---

## 그리드 설계 변경

### 셀 크기: 1.0m → 0.5m (단일 그리드)

벽의 반투과 설계(소형 유닛 통과, 대형 유닛 차단)를 지원하려면, 벽의 경로탐색 점유를 배치 크기보다 작게 설정하여 유닛이 통과할 수 있는 틈을 만들어야 한다. 0.5m 셀이면 패딩 1 기반 Small/Large 구분이 정확히 동작한다.

**배치 그리드와 경로탐색 그리드를 분리하지 않는다**. 맵을 2개 운용하면 동기화 로직과 좌표 변환이 필요해져 복잡도만 증가한다. 단일 0.5m 그리드에서 `GridCell`에 `IsOccupied`(배치)와 `IsPathBlocked`(경로탐색) 두 필드를 유지한다.

### 벽 반투과 동작

벽은 스타크래프트 파일런과 유사한 구조물로, 유저에게는 2칸(2m×2m)으로 보이지만 소형 유닛은 인접 벽 사이를 통과할 수 있다.

```
셀 크기 = 0.5m
벽 배치 크기 = 4×4 셀 (2m × 2m, 유저가 보는 "2칸")
벽 경로탐색 점유 = 중앙 2×2 셀 (1m × 1m)
■ = 경로탐색 차단,  □ = 통과 가능,  X = 패딩에 의해 차단

[빈틈없이 배치] — 벽 시각적으로 붙어있음
  Wall A (4셀)       Wall B (4셀)
  □ ■ ■ □ | □ ■ ■ □

  경로점유: _ ■ ■ _ _ ■ ■ _  (gap = 2셀)
  Small맵:  _ ■ ■ _ _ ■ ■ _  (패딩 0, gap 통과 가능)
  Large맵:  X ■ ■ X X ■ ■ X  (패딩 1, gap 전부 차단)

  Small: 통과 O    Large: 통과 X

[1칸 띄움] — 유저 기준 1칸(1m) 간격
  Wall A (4셀)   gap(2셀)  Wall B (4셀)
  □ ■ ■ □ □ □ □ ■ ■ □

  경로점유: _ ■ ■ _ _ _ _ ■ ■ _  (gap = 4셀)
  Large맵:  X ■ ■ X _ _ X ■ ■ X  (중앙 2셀 통과 가능)

  Small: 통과 O    Large: 통과 O
```

### 구조물 풋프린트 변환

| 구조물 | 물리 크기 | 배치 (Width×Length) | 경로탐색 (PathWidth×PathLength) | 비고 |
|--------|----------|--------------------|-----------------------------|------|
| Wall | 2m × 2m | 4×4 | **2×2** (중앙) | 반투과 |
| Barracks | 3m × 3m | 6×6 | **6×6** (전체) | 완전 차단 |
| Turret | (확인 필요) | (크기에 맞게) | **(=Width)** | 완전 차단 |
| ResourceCenter | 4m × 4m | 8×8 | **8×8** (전체) | 완전 차단 |

벽만 경로탐색 점유가 배치보다 작다. 나머지 건물은 PathWidth = Width (완전 차단).

## 설계 결정 요약

| 항목 | 결정 | 근거 |
|------|------|------|
| 알고리즘 | **Flow Field** (BFS 기반) | 목적지당 1회 계산, 다수 유닛 공유, RTS에 최적 |
| 그리드 셀 크기 | **0.5m** (단일 그리드) | 벽 반투과 설계 지원, 배치/경로탐색 그리드 분리 불필요 |
| 벽 경로탐색 점유 | **배치 중앙 2×2** (배치 4×4의 부분집합) | 인접 벽 사이 소형 유닛 통과, 대형 유닛 차단 |
| 유닛 크기 | 2종 passability 맵 (Small/Large) | Small(패딩 0)은 좁은 통로 통과, Large(패딩 1)는 벽 갭 차단 |
| 경로 스무딩 | 불필요 | Flow Field는 셀 단위로 방향을 제공, 자연스러운 곡선 이동 |
| 벽 충돌 | PredictedMovementSystem 기존 Physics 로직 유지 | 서브셀 정밀도 필요, 경로만 Grid로 전환 |
| Flying 유닛 | 장애물 무시 직선 이동 (동작 변경) | Flow Field 조회 스킵, 목적지 방향으로 직진 |
| 동적 장애물 | GridCell 직접 참조 + 캐시 무효화 | 건물 건설/파괴 시 모든 캐시 필드 폐기 |
| 하위 호환 | MovementWaypoints 유지 | FlowFieldSteeringSystem이 매 프레임 가상 웨이포인트 주입 |

**Small**: Hero, Worker, Striker, Archer, EnemySmall
**Large**: Tank, EnemyBig
**Flying**: EnemyFlying — FlowField를 사용하지 않고 직선 이동 (CellPadding 값 미참조)

## Flow Field 동작 원리

```
1. 유닛이 MoveRequestRpc 수신 → MovementGoal.Destination 설정, IsPathDirty=true

2. FlowFieldSystem (매 프레임):
   ├─ Phase 1: IsPathDirty=true인 유닛 수집 → 고유 목적지 셀 목록 추출
   ├─ Phase 2: 캐시 미스인 목적지에 대해 BFS 계산 (병렬 IJob)
   │   └─ BFS: 목적지 셀에서 출발, 인접 passable 셀로 확산, 각 셀에 방향(byte) 기록
   └─ Phase 3: 유닛에 FlowFieldRef(목적지 셀 키) 할당, IsPathDirty=false

3. FlowFieldSteeringSystem (매 프레임, 이동 중 유닛):
   ├─ 유닛의 현재 셀 → Flow Field에서 방향 조회
   ├─ 방향(byte) → 다음 셀 오프셋 변환 → 다음 셀 중심 월드 좌표 계산
   ├─ [중간 셀] Current = 다음 셀 중심, HasNext = true
   ├─ [목적지 셀] Current = MovementGoal.Destination (실제 월드 좌표), HasNext = false
   └─ PredictedMovementSystem이 기존대로 Current를 향해 이동

4. 도착: MovementArrivalSystem이 기존 로직으로 판정 (HasNext=false && 거리 < ArrivalRadius)
```

**캐시 전략**:
- Flat `NativeArray<byte>` 풀 (`maxFields * gridCellCount`) + `NativeHashMap<int, int>` (destinationKey → poolIndex, 메인 스레드 전용)
- 유닛 크기별 2개 캐시 (Small/Large), 각각 별도 풀
- 최대 32 필드 × 2풀(Small/Large) = 64 필드 (64 * 40KB = 2.56MB, 200x200 그리드 기준)
- LRU 방식 필드 교체
- 그리드 변경 시 전체 캐시 무효화 (BFS ~0.1ms로 재계산 비용 무시 가능)
- passability 맵도 캐싱: `SmallPassabilityMap`/`LargePassabilityMap`을 `IsGridStale` 시에만 재생성 (매 프레임 빌드하지 않음)

## SystemGroup 배치

```
[SimulationSystemGroup - Server]
  GridObstacleResponseSystem        [UpdateBefore(FlowFieldSystem)]
  GridObstacleCleanupSystem         [UpdateAfter(ServerDeathSystem), UpdateBefore(FlowFieldSystem)]
    ↓ UpdateAfter
  FlowFieldSystem (Phase0→Collect→Compute×8→Apply)
    ↓ UpdateAfter
  FlowFieldSteeringSystem
    ↓ UpdateAfter
  PredictedMovementSystem           [UpdateAfter(FlowFieldSteeringSystem)]
```

## Phase 간 의존성 및 권장 실행 순서

Phase 2(FlowFieldSystem)가 `GridPathfindingSize`, `FlowFieldRef` 컴포넌트를 참조하지만, 이 컴포넌트는 Phase 4에서 정의된다. 따라서 Phase 4의 컴포넌트 생성을 Phase 2 이전으로 선행해야 한다.

```
권장 실행 순서:
1. Phase 4-A (선행): 신규 컴포넌트 3종 생성 + GridCell 필드 추가 + MovementGoal [MarshalAs] 추가
2. Phase 0: GridUtility 확장 메서드 구현
3. Phase 1: FlowFieldCore BFS 알고리즘
4. Phase 2: FlowFieldSystem
5. Phase 2.5: FlowFieldSteeringSystem
6. Phase 3: GridObstacleResponseSystem / CleanupSystem
7. Phase 4-B (후행): NavMesh 제거, Authoring 변경, CurrentWaypointIndex 참조 정리
8. Phase 5: 테스트 (EditMode → PlayMode → 성능)
```

### Phase 4-A (선행): 컴포넌트/필드 사전 준비

- [ ] `MovementGoal.IsPathDirty`, `IsPathPartial`에 `[MarshalAs(UnmanagedType.U1)]` 추가
→ 상세: [06-Phase4-컴포넌트정리.md](06-Phase4-컴포넌트정리.md)

### Phase 1: Flow Field 코어 알고리즘

## 검증 방법

1. **벽 반투과 (핵심)**: 벽 일렬 빈틈없이 배치 → Small 유닛 사이로 이동 확인, Large 유닛 차단 확인
2. **벽 1칸 띄움**: 1칸(1m) 간격 배치 → Large 유닛 사이로 이동 확인
3. **기본 이동**: 유닛 이동 명령 → Flow Field 생성 → 목적지 도착
4. **동적 장애물**: 건물 건설/파괴 시 캐시 무효화 → 경로 재계산 확인
5. **대규모 테스트**: 500+ 유닛 스폰 → 프로파일러에서 GPU/CPU 부하 확인
6. **네트워크**: 클라이언트-서버 모드에서 이동 동기화 확인
7. **Flying**: EnemyFlying이 벽 무시하고 직선 이동 확인

## 성능 비교

| 항목 | NavMesh (현재) | Flow Field (전환 후) |
|------|---------------|---------------------|
| 100유닛 동일 목적지 | NavMeshQuery x 100회 | BFS x **1회** |
| 계산 단위 | **유닛당** (N유닛 = N회) | **목적지당** (동일 목적지 공유) |
| managed 객체 | 건물당 NavMeshObstacle GO | **0** |

| 데이터 소스 | NavMesh + Grid + Physics (3중) | **Grid + Physics (2중)** |
| 그리드 셀 수 | 10,000 (100x100, 1m) | **40,000** (200x200, 0.5m) |
| 캐시 메모리 | NavMesh bake (~수 MB) | 64 필드(32×2풀) × 40KB = **2.56MB** |

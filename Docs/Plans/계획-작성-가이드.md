# 실행 플랜 작성 가이드

Claude Code에게 구현 플랜을 요청할 때 따라야 할 가이드라인.
이 문서를 기반으로 플랜을 요청하면, 일관된 구조와 품질의 계획서를 받을 수 있다.

> **이 문서를 참조하는 스킬**: `/plan-create`, `/plan-execute`, `/plan-edit`

---

## 1. 플랜 요청 시 반드시 포함할 정보

| 항목 | 설명 | 예시 |
|---|---|---|
| **변경 대상** | 어떤 시스템/컴포넌트/모듈이 변경되는지 | `CombatSystem`, `MovementAuthoring` |
| **현재 문제** | 지금 왜 안 되는지, 왜 바꿔야 하는지 | "원거리 유닛이 타겟 사망 후 재탐색하지 않음" |
| **원하는 결과** | 변경 후 어떻게 동작해야 하는지 | "타겟 사망 시 AggroTarget 초기화 + 재탐색" |
| **제약 조건** | 하위 호환, 데이터 마이그레이션, 성능 제약 등 | "기존 Ghost 동기화 구조 유지" |

## 2. 플랜 산출물 구조

플랜은 아래 3가지 문서로 구성된다.

### 2-1. 오케스트레이션 파일 (orchestration.md)

전체 플랜의 **중심 문서**. 문제 정의, AS-IS/TO-BE, Phase 체크리스트를 포함한다.

```markdown
# [기능명] 오케스트레이션 플랜

## 문제 정의
- 현재 상황에서 무엇이 문제인지 구체적으로 기술
- 영향 범위 (어떤 시스템, 어떤 컴포넌트, 어떤 데이터에 영향을 주는지)

## AS-IS (현재 상태)
- 현재 상태 흐름도 또는 목록
- 관련 파일/클래스 목록
- 현재 동작 방식 요약

## TO-BE (목표 상태)
- 변경 후 상태 흐름도 또는 목록
- 삭제/추가/변경되는 항목 명시
- 기대 동작 방식 요약

## AS-IS vs TO-BE 비교표
| 항목 | AS-IS | TO-BE |
|---|---|---|
| ... | ... | ... |

## Phase 체크리스트

### Phase 1: [제목]
- [ ] 작업 항목 1
- [ ] 작업 항목 2
→ 상세: [phase-1-[제목].md](./phase-1-[제목].md)

### Phase 2: [제목]
- [ ] 작업 항목 1
→ 상세: [phase-2-[제목].md](./phase-2-[제목].md)

## Phase 간 의존성
| Phase | 의존성 | 병렬 가능 |
|---|---|---|
| 1 | 없음 | - |
| 2 | Phase 1 | X |
| 3 | Phase 1 | O (Phase 2와 병렬) |

## 변경 파일 요약
| Phase | 파일 | 변경 |
|---|---|---|
| 1 | `path/to/file.cs` | 변경 내용 |

## 검증 방법
1. 검증 항목 1
2. 검증 항목 2

## 롤백 전략
- Phase별 롤백 방법
```

### 2-2. Phase 파일 (phase-N-[제목].md)

각 Phase의 **구체적인 실행 계획**.

```markdown
# Phase N: [제목]

## 목표
- 이 Phase에서 달성해야 할 것

## 선행 조건
- 이 Phase 시작 전에 완료되어야 할 것

## 작업 목록

### Task 1: [작업명]
- [ ] 상세 작업 1
- [ ] 상세 작업 2

### Task 2: [작업명]
- [ ] 상세 작업 1

## 병렬 작업 구성 (subagent 활용)

> 독립적인 작업은 subagent로 병렬 실행하여 효율을 높인다.

| Agent | 작업 내용 | 의존성 |
|---|---|---|
| Agent A | Task 1 실행 | 없음 |
| Agent B | Task 2 실행 | 없음 |
| Agent C | Task 3 실행 | Agent A, B 완료 후 |

## 테스트 요구사항

> 변경된 로직은 반드시 테스트로 검증한다.

### EditMode Test
- 순수 함수, 유틸리티 메서드에 대한 단위 테스트
- 경계값, 예외 케이스 포함

### PlayMode Test (필요 시)
- ECS 시스템 통합 테스트
- World 생성 → 엔티티 구성 → 시스템 실행 → 결과 검증 흐름

## 검증 방법
- 이 Phase 완료를 확인하는 방법 (테스트 통과, 컴파일 성공, 수동 확인 등)

## 완료 기준
- [ ] 기준 1
- [ ] 기준 2
- [ ] EditMode Test 통과
- [ ] PlayMode Test 통과 (해당 시)
```

### 2-3. 실행 기록 (execution-log.md)

**계획 실행 과정**을 기능 단위로 기록한다. 날짜 기반 WorkLog와 달리, 한 계획의 전체 실행 이력을 한 곳에서 추적할 수 있다.

> **WorkLog와의 역할 분리**: 계획 기반 작업은 `execution-log.md`에 기록한다. `Docs/WorkLog/`는 계획 없이 수행한 단발 작업(핫픽스, 즉석 수정)에만 사용한다.

```markdown
# 실행 기록

## Phase 1: [제목] - [날짜]

### 실행 내역
| 작업 | 결과 | 비고 |
|---|---|---|
| Explore agent로 영향 범위 조사 | 완료 | 관련 파일 5개 발견 |
| ArrivalUtility 메서드 추가 | 완료 | |

### 변경된 파일
- `path/to/file.cs` - 변경 내용 요약

### 발견된 이슈
- [이슈 설명] → [대응 방법]

### Phase 1 완료 판정: Pass / Fail

---

## Phase 2: [제목] - [날짜]
...
```

## 3. 플랜 작성 시 주의사항

### 3-1. 문제 정의를 충분히 하라
- 코드를 바꾸기 전에 **왜 바꿔야 하는지**를 먼저 정리
- "~하면 좋겠다"가 아닌 "현재 ~가 문제이고, ~때문에 ~가 발생한다" 형식

### 3-2. AS-IS를 코드 기반으로 검증하라
- 추측이 아닌 실제 코드를 읽고 AS-IS를 작성
- 관련 파일 경로, 메서드명, 컴포넌트명 등을 구체적으로 명시
- Explore agent를 활용하여 코드베이스를 충분히 조사한 후 작성

### 3-3. Phase는 롤백 가능한 단위로 나눠라
- 한 Phase가 실패해도 이전 Phase까지는 안전한 상태여야 함
- 구조적 변경(컴포넌트 추가/삭제)이 포함된 Phase는 영향 범위를 명확히 기술

### 3-4. 병렬 작업은 의존성이 없을 때만
- 서로 같은 파일을 수정하는 작업은 병렬로 하지 않는다
- 병렬 작업 간 merge conflict가 발생할 수 있는 경우 순차 실행

### 3-5. 검증을 Phase마다 넣어라
- 각 Phase 완료 후 반드시 검증 단계를 포함
- 테스트 실행, 컴파일 확인 등 구체적인 검증 방법 명시
- 검증 실패 시 다음 Phase로 넘어가지 않는다

### 3-6. 하위 호환을 고려하라
- Ghost 동기화 컴포넌트 변경 시 네트워크 영향 확인
- 컴포넌트 삭제 시 기존 Authoring/Prefab 영향 확인
- 삭제하려는 코드가 다른 곳에서 참조되는지 Grep으로 확인

## 4. 디렉토리 구조

```
Docs/Plans/
├── [기능명]/                         # 기능별 플랜 폴더
│   ├── orchestration.md             # 오케스트레이션 (중심 문서)
│   ├── phase-1-[제목].md            # Phase 1 상세
│   ├── phase-2-[제목].md            # Phase 2 상세
│   ├── ...
│   └── execution-log.md             # 실행 기록 (이 계획의 실행 이력)
├── Completed/                       # 완료된 계획 보관
│   └── [기능명]/
└── 계획-작성-가이드.md               # 이 문서
```

## 5. 완료 후 처리

계획의 모든 Phase가 완료되면:
1. `Docs/Systems/` 진리 문서를 최신 상태로 업데이트한다
2. 계획 폴더를 `Docs/Plans/Completed/`로 이동한다

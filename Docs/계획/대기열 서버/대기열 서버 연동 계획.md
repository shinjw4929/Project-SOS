# 매칭/대기열 서버 연동 계획 (Unity 측)

> **전제**: C++ 매칭/대기열 서버가 완성된 상태에서 Unity 프로젝트에 적용하는 작업 계획.
> 큐 서버 주소: `:8080` (TCP), 내부 채널: `:8081` (TCP), 게임 서버 주소: `:7979` (Netcode for Entities)
> **프로토콜 정의**: [`queue.proto`](queue.proto) (Single Source of Truth, C++ 서버 문서와 공통 참조)

---

## 1단계: Protobuf 환경 구성 및 코드젠

### 목표
`queue.proto`에서 C# 코드를 생성하고, Unity 프로젝트에 통합한다.

### 작업 내용

| 파일 | 위치 | 설명 |
|------|------|------|
| `queue.proto` | `Proto/` (submodule) | 공유 메시지 스키마 |
| 생성된 C# 코드 | `Client/Network/Generated/` | protoc --csharp_out 결과물 |

### 설정
- NuGet: `Google.Protobuf` 패키지 Unity에 추가 (dll 직접 임포트 또는 NuGetForUnity)
- `protoc` 실행: proto/ 디렉토리의 queue.proto → C# 코드 생성
- 프레이밍: 4byte 길이 접두사(little-endian) + Protobuf Envelope 바이너리

### 주의사항
- Protobuf C# 런타임은 managed 코드이므로 Burst/Job에서 직접 사용 불가
- 네트워크 레이어(QueueClient, QueueTokenValidator)가 managed 코드이므로 문제없음
- ECS와의 데이터 전달은 단순 값 복사 (토큰 문자열 → FixedString64Bytes)

## 3단계: 큐 클라이언트 구현

### 목표
큐 서버와 TCP 통신하는 MonoBehaviour를 작성한다. DOTS 외부(managed)에서 동작한다.

### 작업 내용

| 파일 | 위치 | 설명 |
|------|------|------|
| `QueueClient.cs` | `Client/Network/` | TCP 비동기 통신, Protobuf Envelope 송수신 |
| `QueueAuthState.cs` | `Client/Component/Singleton/` | 매칭 결과(토큰, teamId)를 ECS에 전달하는 싱글톤 |

#### QueueClient.cs 핵심 로직

```
1. 앱 시작 시 큐 서버(:8080)에 TCP 접속
2. Envelope(MatchRequest(player_id)) 전송
3. 수신 루프 (Envelope.PayloadCase 분기):
   - QueueStatusUpdate → UI 갱신 (순번, 대기 인원, 예상 대기 시간)
   - MatchFound → 토큰 + teamId 저장 + Netcode 연결 트리거
   - RejectResponse → 에러 UI 표시 (reason별 분기)
4. 주기적 Envelope(Heartbeat) 전송 (10초 간격)
5. 게임 서버 연결 성공 시 큐 서버 TCP 연결 종료
```

#### 기술 선택

```
비동기 방식: async/await + TcpClient (System.Net.Sockets)
직렬화: Google.Protobuf (Envelope 파싱)
스레딩: 메인 스레드 차단 없음 (NetworkStream.ReadAsync/WriteAsync)
ECS 연동: QueueAuthState 싱글톤에 토큰/teamId 기록 → GoInGameClientSystem이 읽음
```

#### 생명주기 관리

```
생성: 앱 시작 씬(InGame.unity) 로드 시 자동 생성 (씬에 배치 또는 RuntimeInitializeOnLoadMethod)
유지: DontDestroyOnLoad — 씬 전환 시 파괴 방지
파괴: Application.quitting 이벤트에서 TCP 정리 (TcpClient.Close)

OnDestroy():
  - 수신 루프 CancellationToken 취소
  - TcpClient.Close() (큐 서버에 연결 끊김 통지)
  - Heartbeat 코루틴 중지

재접속 흐름 (게임 종료 후 재매칭):
  1. 게임 종료 시 Netcode Disconnect
  2. QueueClient는 DontDestroyOnLoad로 살아있음
  3. QueueClient.StartMatchmaking() 호출 → 큐 서버에 재접속 + MatchRequest
  4. 새 매칭 → 새 토큰 → 새 Netcode 연결
  5. QueueAuthState 싱글톤 초기화 (이전 토큰 제거)
```

#### 상태 흐름

```
[Disconnected] → Connect → [Connecting] → 접속 성공 → [Waiting]
[Waiting] → QueueStatusUpdate 수신 → [Waiting] (UI 갱신)
[Waiting] → MatchFound 수신 → [Matched] → Netcode 연결 트리거
[Matched] → Netcode 연결 성공 → [InGame] → 큐 TCP 종료
[InGame] → 게임 종료 → [Disconnected] → 재매칭 가능
[Waiting] → CancelMatchRequest 전송 → [Disconnected]
[*] → 오류/타임아웃 → [Error] → 재시도 또는 에러 UI
```

## 4단계: GoInGameRequestRpc 토큰 추가 및 서버 검증

### 목표
게임 서버가 큐 서버를 거치지 않은 직접 접속을 거부할 수 있도록 토큰 검증을 추가한다.

### 작업 내용

#### 4-1. RPC 수정

**파일**: `Assets/Scripts/Shared/RPCs/GoInGameRequestRpc.cs`

```csharp
public struct GoInGameRequestRpc : IRpcCommand
{
    public FixedString64Bytes AuthToken;  // 큐 서버 발급 토큰
}
```

#### 4-2. QueueSessionInfo 컴포넌트 (session_id 저장)

**파일 (신규)**: `Assets/Scripts/Shared/Components/QueueSessionInfo.cs`

```csharp
// 토큰 검증 성공 시 Connection 엔티티에 부착.
// SlotNotifySystem이 연결 끊김 시 이 정보를 읽어 SlotReleased를 전송.
public struct QueueSessionInfo : IComponentData
{
    public FixedString64Bytes SessionId;
    public FixedString64Bytes PlayerId;
}
```

**session_id / auth_token 흐름 정리**:

```
1. 큐 서버: 매칭 성립 → MatchFound(session_id, auth_token, ...) → 클라이언트

2. 클라이언트: auth_token을 GoInGameRequestRpc에 담아 게임 서버에 전송
   (session_id는 클라이언트가 직접 사용하지 않음)

3. TokenValidationSystem: auth_token으로 큐 서버에 검증 요청
   → TokenValidateResponse(valid, player_id, session_id) 수신
   → 검증 성공 시:
     a. RPC 엔티티에 TokenValidatedTag 부착
     b. SourceConnection 엔티티에 QueueSessionInfo(session_id, player_id) 부착

4. GoInGameServerSystem: TokenValidatedTag 있는 RPC만 처리 → Hero 생성

5. SlotNotifySystem: Connection 끊김 감지
   → QueueSessionInfo에서 session_id, player_id 읽기
   → Envelope(SlotReleased(player_id, session_id)) 전송
```

#### 4-3. TokenValidationSystem (핵심 설계)

**파일 (신규)**: `Assets/Scripts/Server/Systems/TokenValidationSystem.cs`

```
설계: managed SystemBase (Burst 미적용)
실행: SimulationSystemGroup, UpdateBefore(GoInGameServerSystem)
역할: GoInGameRequestRpc를 가로채서 토큰 검증 후 태그 + 세션 정보 부착

구조:
  - [WorldSystemFilter(WorldSystemFilterFlags.ServerSimulation)]
  - partial class TokenValidationSystem : SystemBase (managed, Burst 없음)
  - OnCreate: QueueTokenValidator 인스턴스 생성 (큐 서버 :8081 전용 TCP 연결)
  - OnUpdate:
    1. GoInGameRequestRpc + ReceiveRpcCommandRequest 쿼리 (WithNone<TokenValidatedTag>)
    2. 각 RPC에서 AuthToken 추출
    3. QueueTokenValidator.Validate(token) 호출 (동기 TCP, 내부 채널이므로 < 1ms)
    4. 유효:
       - RPC 엔티티에 TokenValidatedTag 부착
       - SourceConnection에 QueueSessionInfo(sessionId, playerId) 부착
    5. 무효: SourceConnection에 NetworkStreamRequestDisconnect 부착 + RPC 엔티티 파괴

태그 컴포넌트:
  public struct TokenValidatedTag : IComponentData { }

GoInGameServerSystem은 기존 쿼리에 WithAll<TokenValidatedTag>만 추가하면 됨.
```

```csharp
// TokenValidationSystem 핵심 구조 (pseudo)
[UpdateBefore(typeof(GoInGameServerSystem))]
[WorldSystemFilter(WorldSystemFilterFlags.ServerSimulation)]
partial class TokenValidationSystem : SystemBase
{
    private QueueTokenValidator _validator;

    protected override void OnCreate()
    {
        _validator = new QueueTokenValidator("127.0.0.1", 8081);
        RequireForUpdate<GoInGameRequestRpc>();
    }

    protected override void OnUpdate()
    {
        var ecb = new EntityCommandBuffer(Allocator.Temp);
        foreach (var (rpc, request, entity) in
            SystemAPI.Query<RefRO<GoInGameRequestRpc>, RefRO<ReceiveRpcCommandRequest>>()
                .WithNone<TokenValidatedTag>()
                .WithEntityAccess())
        {
            string token = rpc.ValueRO.AuthToken.ToString();
            var result = _validator.Validate(token);

            if (result.Valid)
            {
                ecb.AddComponent<TokenValidatedTag>(entity);
                ecb.AddComponent(request.ValueRO.SourceConnection,
                    new QueueSessionInfo
                    {
                        SessionId = result.SessionId,
                        PlayerId = result.PlayerId
                    });
            }
            else
            {
                ecb.AddComponent<NetworkStreamRequestDisconnect>(
                    request.ValueRO.SourceConnection);
                ecb.DestroyEntity(entity);
            }
        }
        ecb.Playback(EntityManager);
    }

    protected override void OnDestroy()
    {
        _validator?.Dispose();
    }
}
```

#### 4-4. QueueTokenValidator

**파일 (신규)**: `Assets/Scripts/Server/Network/QueueTokenValidator.cs`

```
역할: 큐 서버 내부 채널(:8081)에 Envelope(TokenValidateRequest) 전송 → TokenValidateResponse 수신
방식: managed 클래스, TcpClient 동기 조회 (로컬 < 1ms)
수명: TokenValidationSystem.OnCreate에서 생성, OnDestroy에서 Dispose
연결: 전용 TCP 연결 1개 (TokenValidationSystem 전용)
프로토콜: queue.proto의 Envelope (TokenValidateRequest/Response)
```

#### 4-5. GoInGameServerSystem 수정

**파일**: `Assets/Scripts/Server/GoInGameServerSystem.cs`

```
변경 사항 (최소):
1. 기존 쿼리에 .WithAll<TokenValidatedTag>() 추가
2. 나머지 로직 변경 없음 — [BurstCompile] 유지 가능

토큰 검증은 TokenValidationSystem이 이미 처리했으므로,
GoInGameServerSystem은 TokenValidatedTag가 있는 RPC만 통과시킴.
```

#### 4-6. SlotNotifySystem (SlotReleased 전송 주체)

**파일 (신규)**: `Assets/Scripts/Server/Systems/SlotNotifySystem.cs`

```
설계: managed SystemBase (Burst 미적용, TCP 통신 필요)
실행: SimulationSystemGroup
역할:
  1. 연결 끊김 감지: QueueSessionInfo가 있지만 Connection이 끊긴 엔티티 감지
  2. SlotReleased 전송: session_id + player_id를 읽어서 큐 서버에 전송
  3. GameServerHeartbeat: 30초 간격으로 전송

TCP 연결: 별도 TCP 연결 1개 (QueueTokenValidator와 독립)
  → 이유: TokenValidateRequest는 요청-응답 패턴이고,
    SlotReleased/GameServerHeartbeat는 일방향 전송.
    하나의 연결을 공유하면 수신 측에서 응답 매칭(request-id)이 필요.
    localhost 통신이므로 연결 2개의 오버헤드는 무시할 수 있고,
    로직이 단순해지는 이점이 크다.

구체적 동작:
  - OnCreate: SlotNotifyClient 인스턴스 생성 (큐 서버 :8081 별도 TCP 연결)
  - OnUpdate:
    a. QueueSessionInfo가 있는 Connection 엔티티 중 끊긴 것 탐지
       → QueueSessionInfo에서 SessionId, PlayerId 읽기
       → Envelope(SlotReleased(playerId, sessionId)) 전송
       → QueueSessionInfo 컴포넌트 제거 (중복 전송 방지)
    b. 30초마다 Envelope(GameServerHeartbeat(active_player_count)) 전송
  - 전송 실패 시 (큐 서버 다운): 로그 경고 후 무시
    → 큐 서버 측은 하트비트 TTL(90초) 만료로 슬롯 자동 복구

비정상 종료 시나리오:
  - 게임 서버 크래시: SlotReleased도 GameServerHeartbeat도 안 나감
  - 큐 서버 측 대응: game_server:{serverId} Redis 키 TTL 90초 만료
    → 해당 서버의 모든 세션 자동 정리 → 슬롯 복구
```

#### TCP 연결 요약

```
게임 서버(:7979) → 큐 서버(:8081)

연결 1 (TokenValidationSystem 전용):
  요청-응답 패턴
  TokenValidateRequest → TokenValidateResponse

연결 2 (SlotNotifySystem 전용):
  일방향 전송 패턴
  SlotReleased → (응답 없음)
  GameServerHeartbeat → (응답 없음)

두 연결 모두 서버 시작 시 수립, 종료 시 정리.
localhost 통신이므로 연결 2개의 리소스 비용은 무시 가능.
```

## 6단계: 에러 처리 및 엣지 케이스

### 처리해야 할 시나리오

| 시나리오 | 처리 주체 | 처리 방법 |
|---------|----------|----------|
| 큐 서버 접속 실패 | QueueClient | 재시도 UI 표시 (3회 후 에러 화면) |
| 대기 중 큐 서버 연결 끊김 | QueueClient | 자동 재접속 시도, 순번 복원 요청 |

| 게임 중 연결 끊김 | Netcode 기본 처리 | 기존 Disconnect 로직 |
| 큐 없이 직접 :7979 접속 | TokenValidationSystem | 빈 토큰 → 검증 실패 → Disconnect |

| 게임 종료 후 재매칭 | QueueClient | DontDestroyOnLoad → StartMatchmaking() 재호출 |

## 작업 순서 및 의존성

```
[1단계] Protobuf 환경 구성 ──────────────────────┐
                                                  │
[2단계] 자동 연결 비활성화 + 수동 연결 인프라 ──┐ │
                                              │ │
[3단계] 큐 클라이언트 (QueueClient.cs) ◄──────┴─┘
    │
    ├──► [4단계] 토큰 검증 (TokenValidationSystem + SlotNotifySystem)
    │
    └──► [5단계] 매칭/대기열 UI
              │
              ▼
         [6단계] 에러 처리 + 테스트
```

- 1단계는 C++ 큐 서버의 queue.proto 확정 직후 시작 (이미 확정됨 — queue.proto 참조)
- 2단계와 1단계는 병렬 진행 가능
- 3단계는 1단계(Protobuf 코드젠) + 2단계(수동 연결) 완료 후 시작
- 4, 5단계는 3단계 완료 후 병렬 진행 가능
- 6단계는 전체 통합 후 마무리
